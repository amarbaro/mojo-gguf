# mojo-gguf v0.1.0

**Released:** 2026-10-26 · **Commit:** the one tagged `v0.1.0` · **Previous:** first release

## What it does

GGUF tools in Mojo that write the bytes llama.cpp's own tools write: a GGUF reader and writer, the four gguf-py
scripts, the Qwen2 safetensors-to-GGUF converter, the LoRA and legacy-GGML converters, eight `llama-quantize --pure`
types and a dequantizer for 19 types. Each is compared with llama.cpp pinned at `1744c6bde`. Linux x86-64, CPU only,
Mojo 1.1.

## Highlights

- `hf2gguf` and `quantize --pure` produce the same bytes as `convert_hf_to_gguf.py` (bf16, q8_0) and `llama-quantize
  --pure` (8 types) on Qwen2.5-0.5B-Instruct, in 0.3 to 0.9 s and 33 to 50 MiB peak RSS instead of 0.8 to 12.6 s and
  0.9 to 2.2 GiB.
- `gguf-dequant` is bit-equal to `ggml`'s `to_float` for all 19 types it covers, including Q2_0, TQ1_0 and the IQ
  types.
- `gguf-tool`, `ggml2gguf`, `lora2gguf` and `hf-update` match the Python scripts in stdout, exit code and written
  bytes on the gate cases.

## Known limits

- Converters and `lora2gguf` handle Qwen2 only; `quantize` handles `--pure` only; other inputs are a `FAIL`.
- The converter, quantizer, dequant and LoRA gates run locally, not in CI: they need a llama.cpp build, torch and the
  model.
- Byte-identity is shown on the gate inputs, not proven for every model.

## Upgrade / run

```
git clone https://github.com/amarbaro/mojo-gguf && cd mojo-gguf && uv sync
mojo build -I src src/gguf_rewrite.mojo -o gguf-rewrite
```
